# Responsive and cross-platform accessibility — Prompt 7

## Architecture and impact map

Web is React/Vite with Tailwind and the existing scoped Radix/shadcn-style primitives. Tauri macOS/Windows uses those same web assets and semantic tokens. Expo React Native owns native controls and consumes the generated design-token palette; it never imports DOM components. Domain/API/validation/settings persistence remain shared and unchanged.

The only new dependency is mobile `react-native-safe-area-context` 5.10.1, pinned to the version recommended by the **installed** Expo SDK's `bundledNativeModules.json`. It supplies actual cutout/home-indicator insets instead of guessing bottom/landscape padding. [Expo guidance](https://docs.expo.dev/versions/latest/sdk/safe-area-context/) calls for a root provider and modal providers where necessary. No new framework, router, component library, settings system or font package was introduced.

## Findings and changes

- Collapsed web navigation previously hid the focused section button after keyboard selection. The existing toggle now names its controlled section list; selection and Escape return focus to the visible toggle while preserving destinations, permissions and current-section state. Desktop Escape still dismisses the existing rail label. Crossing the existing 1024px breakpoint moves focus from a newly hidden rail item to the visible toggle, and from a newly hidden toggle to the current desktop item when widening; unrelated focused controls keep focus.
- At 200% text size, the menu's 12rem minimum exceeded the viewport despite its maximum width. The minimum is now capped by available viewport width; items can wrap long text. Existing Radix keyboard navigation, disabled-item skipping, portals, collision handling and dismissal are retained.
- Dialogs retain focus containment, initial Cancel, Escape and original confirmation behavior. Scroll containment and wrapping protect long content on short screens. Native confirmations use a bounded ScrollView and real safe-area padding.
- Native shell previously padded only Android's status-bar height and had no bottom/landscape inset ownership. AppViewport uses the existing theme, safe-area view and one ScrollView. iOS automatic keyboard insets avoid overlapping fields; Android retains the platform's window resize behavior. Handled taps still activate controls while the keyboard is present, and dragging dismisses the keyboard without changing drafts.
- Native alert text defaults to an assertive announcement; explicit live-region choices still win. Passive content remains passive. Existing POS progress/uncertain/quote state is a polite live region on both platforms; offline/server-confirmed meaning and mutation safeguards remain unchanged.
- Token showcase rows wrap at enlarged text; no token, color or semantic status changed. Existing exact-value table overflow regions, labelled native record rows, touch targets and theme/preferences are reused.

## Verification scope

The browser regression file is `tests/browser/responsive-accessibility.spec.ts`. `tests/manual/responsive-accessibility.mjs` extends the existing disposable PostgreSQL/API/browser fixture: every implemented workspace section is checked at 200% text (32px root and doubled semantic type scale), at 320×480, 640×360, 1024×600 and 2560×1440. This is text enlargement/reflow evidence, not a claim of browser-chrome zoom or assistive-technology certification. Existing light/dark, large/small preference, table overflow, reduced-motion, focus, axe and financial-workflow checks are retained.

Native component tests replace only the unavailable safe-area bridge with a documented jsdom adapter; emulator checks are required to prove actual insets and keyboard behavior. Windows cannot run on this macOS host; only Apple Command Line Tools are installed, so iOS simulator/device execution remains unavailable. Neither Expo JS exports nor React Native Web tests qualify native production builds or physical scanner/printer hardware.

Widening chooses the current section, with the first available item as a fallback; narrowing uses the visible toggle. A visible unrelated control keeps focus in either direction.
