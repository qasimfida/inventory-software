# Validation and acceptance

## Available today

[README commands](../../README.md) are the canonical command reference. `validate` runs formatting, documentation/source review thresholds, ESLint/import boundaries, strict type checks including test/tooling code, tooling regression tests, Vitest, and shared/API/web builds. Set a valid `VITE_API_BASE_URL` or copy the example environment before validation. `build:mobile` separately exports Android/iOS JS bundles and Expo web. `build:desktop` requires native toolchains. Do not interpret JS export as a native release build.

`npm test` first runs Node tooling regression tests (forbidden import probes and JavaScript lint enforcement), then Vitest. Vitest includes `.test.ts` and `.test.tsx`, resolves the web `@/` alias, and covers server-rendered UI state semantics, environment rejection/redaction, typed transport responses, versioned HTTP health, CORS, headers, error envelopes and request validation. Nest test compilation uses TypeScript's legacy decorators/metadata through a small pre-transform; it does not weaken application types. `test:integration` requires `TEST_DATABASE_URL` and fails explicitly without it; it queries real PostgreSQL and closes the pool. Entry smoke tests now cover real browser mounting in jsdom, Expo registration with a browser-native renderer, the real Nest application factory, and shared compiled exports. Native desktop tests generate the real Tauri context. Workspace scripts select only their own tests; see [workspace commands](workspace-boundaries.md). Command 4 adds a focused Playwright browser check for the foundation design system at 320px and 1440px, including axe accessibility checks and modal focus. It does not test business workflows. See [design system checks](design-system.md).

The foundation checker validates local Markdown file targets, required documents and source-size review warnings. It does not validate heading anchors or external links. Generated native/build directories are excluded. Dependency-cruiser enforces cycles, resolution and app/shared/runtime boundaries; strict shared-package configs omit DOM/Node globals. Review runtime behavior in addition to these structural checks.

Keep tests adjacent to implementations (`.test.ts`/`.test.tsx`); PostgreSQL tests use `.integration.test.ts`. Native tests need the corresponding OS/device. A future CI service should run the same commands but is not introduced under this task's scope. Record current check evidence in the [foundation audit](foundation-audit.md); the [Command 1 record](validation-status.md) is historical. never use success-only stubs for unavailable runners.

| Change             | Minimum evidence                                                                                                                                                                |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Pure domain rule   | Unit examples and boundaries; rounding, quantities and invariants where relevant                                                                                                |
| API/schema         | Runtime contract validation, authorization negatives, PostgreSQL integration; clean and upgrade migration paths                                                                 |

| Native integration | Actual target OS build plus device/emulator or hardware evidence relevant to printing/scanning/storage                                                                          |

Use real PostgreSQL for SQL transaction, isolation and RLS checks; an in-memory mock cannot prove them. Contract tests run against every supported persistence adapter. Exercise persisted state across restarts, not only a network toggle. Never silently discard unsent work during test cleanup of recovery scenarios.

Feature acceptance records behavior, tenant permissions, confirmed/provisional semantics, applicable platform evidence and missing foundation blockers. Run focused checks first, then required package/production checks; repeat only when changes or failures justify it. Report skipped checks and why.

Backend foundation integration tests use `TEST_DATABASE_URL` against real PostgreSQL. They create uniquely named temporary schemas and remove them afterward, verifying commit/rollback, parameter binding, expired transaction scopes, statement timeout recovery, pool draining, migration idempotency, rollback and atomic failure. Use a disposable database with schema-creation permission. Unit tests cover safe logging, rollback cleanup failure, configuration and HTTP validation. See [backend foundation status](backend-foundation.md).

Authentication integration tests require a disposable PostgreSQL role with CREATEDB in `TEST_DATABASE_URL`. They create and drop a uniquely named database, apply real migrations, and exercise HTTP invitation, login, expiration, renewal races, revocation, account isolation, CSRF and rate limits. Client tests cover cookie/bearer separation, storage failures, serialized rotation, offline logout failure, UI locking and the mobile secure-store adapter. See [authentication policy](../security/authentication.md).

Development fixture tests under `apps/api/src/development` additionally exercise all seven documented logins, browser cookies, the backend permission matrix, platform/tenant isolation, idempotent seeding, account collision protection and explicit credential reset/session revocation. They use uniquely named `inventory_dev_*` disposable databases; ordinary integration fixtures retain `auth_test_*` names. `npm run db:seed:dev` is a separate local operator command, never a test or production startup hook. See [test account setup and verification](test-accounts.md).

Organization management adds PostgreSQL tenant-isolation and lifecycle suites, portable stale-response/logout tests, native management component interaction tests and a real-browser scenario. See [Command 7 validation](organization-management.md#validation-results) for commands, test environment and exact platform limitations.

The [eight-command rollout](domain-rollout.md#final-validation--19-october-2026) records the current 61 unit/component, 12 tooling and 41 PostgreSQL test results. Catalog/pricing, stock concurrency/reversal/reservation, purchasing, storage hierarchy and transfer lifecycle suites live beside their modules. The manual real-browser scenario now imports `tests/manual/{catalog,pricing,inventory,purchasing,storage,transfers}.mjs`; supply an isolated migrated API/web server, `E2E_WEB_URL` and `E2E_INVITATION`. It creates business records and must run against disposable data. It checks axe after the complete workflow. Mobile exports and macOS packaging are distinct from installed native/device tests.

Commerce regression suites include `customers/*.integration.test.ts`, `sales/*.integration.test.ts` and `payments/shifts.integration.test.ts`; they run through `npm run test:integration` against an explicitly disposable `TEST_DATABASE_URL`. `tests/manual/organization.mjs` includes customer and full POS/cash/correction browser flows. Build the API/shared packages before launching that test; avoid concurrent rebuilds/HMR while testing a live Vite page. Shared POS-model tests cover unknown/malformed responses, same-command retries, duplicate clicks and stale responses after locking. Native POS controls are exercised through React Native Web in jsdom; that does not replace native device tests.
