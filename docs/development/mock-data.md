# Local demonstration data

Run `npm run dev:mock:web`, `npm run dev:mock:mobile`, or `npm run dev:mock:desktop`. These explicitly set `VITE_USE_MOCKS=true` / `EXPO_PUBLIC_USE_MOCKS=true`. Normal commands never enable mocks. The desktop command uses the same web transport; mobile uses native components. No backend or database is required to browse the demo.

Sign in with any syntactically valid email and nonempty password in the clearly marked demo build, or change Role/Scenario to enter a demo session. These are not production credentials. Superadmin, owner, manager, cashier, inventory operator, accountant and viewer use the existing permission definitions. Choose a role in the demo toolbar or sign in as `superadmin@demo.example.test`, `owner@demo.example.test`, `manager@demo.example.test`, `cashier@demo.example.test`, `inventory@demo.example.test`, `accountant@demo.example.test`, or `viewer@demo.example.test` with a nonempty demo password. Scoped roles have the Central store/Main warehouse assignment. Only superadmin has platform-directory and platform-overview access. Two businesses are available in Settings → Business. The role switch recreates the demo workspace and clears screen state. Normal, empty, error and offline scenarios are deliberate test conditions. Account preferences persist in the demo process per role and reset when reloading the process; real account persistence is unchanged.

`packages/api-client/src/mock` owns all fixtures and transport handlers. The explicit `@inventory/api-client/mock` subpath is dynamically imported only behind development guards. It is not exported by the normal API-client barrel. Runtime response schemas remain active. Vite and Expo reject production builds with a mock flag. No mock handler falls through to fetch, the real API, native credential storage or a real offline vault. Demo vault storage is separate in-memory storage. Errors do not mean a real server was contacted.

Fixtures cover organization, membership, catalog/pricing, stock and movements, counts, storage, purchasing and partial receipts/returns/invoices, transfers, customers/overdue credit, POS quotes, sales/receipts, shifts, payables, reports, notifications/approvals, audit, settings, trading and accounting views. Catalog, purchase, sale and customer lists have enough rows for pagination/search. Long labels and low/zero stock exercise layout edges. Search remains bounded and respects the selected role.

## Deliberate simulation limits

This is a presentation fixture adapter, not a replacement business backend. Read routes, POS pricing previews, local account preferences and notification read state are simulated. Inventory/financial writes, business creation, password recovery, provider calls and offline-grant preparation return an error rather than pretending to post a transaction. Use the live local API and isolated database integration suite to test those workflows. Fixture documents illustrate independent lifecycle states; they are not an end-to-end accounting dataset. Reports derive displayed totals from fixture records, but are not financial assurance evidence. No external payment provider is enabled.

The mock offline scenario tests failure presentation, not durable device synchronization. Real outbox/restart behavior remains covered by the existing offline tests and requires native/device qualification. Never use a demo response as proof of backend authorization or accounting integrity.

Platform overview, registration history, business location counts, directory details and restricted diagnostics now have explicit fixtures. These remain visibly isolated demo data. Use the seven development accounts documented in README against the real local API for transaction testing; demo mode never pretends to commit stock or money.

## Visual QA fixture additions — 2026-10-24

The existing shared mock adapter now includes 26 staff records and 26 salary/expense documents, including inactive staff, unpaid and partially paid costs, and payment detail. The adapter uses the real 25-row page size, search and runtime schemas, with `users.write` required. Mutations remain explicitly unsupported. Inventory overview fixtures now carry their product identity and resolved price so details/edit controls and prices can be inspected on both DOM and native clients. These records are development-only and do not create real payroll, expenses, cash or journals.

Run route matrices only after shared builds have finished. Rebuilding shared packages while Vite/Metro is serving demos can reload the application and reset its intentionally in-memory demo session. The web runner waits for the existing debounced queries before capturing screens.
