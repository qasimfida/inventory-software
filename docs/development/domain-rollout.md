# Eight-command domain rollout

Historical stage report. Offline, synchronization, counts and scanning were added subsequently; current behavior is recorded in [offline rollout](offline-rollout.md).

The user explicitly requested all eight attached commands sequentially. Each step is validated before the next; existing unrelated changes are preserved. Web and desktop share DOM screens; native mobile gets equivalent controls. Physical-device, Windows and signing limitations remain in the platform guide.

## 1. Roles and scoped permissions

Implemented in `contracts/permissions.ts`, `organization/access.ts`, `OrganizationScope`, the membership service, and the web/mobile assignment and audit screens. Migration `1792600000000_permissions.sql` adds scoped memberships, cashier/custom roles, platform administrators and scope indexes on audit events. Existing owner/manager/viewer memberships keep their original business-wide scope.

Permissions use explicit `.read` and `.write` names for business settings, locations, products, stock, sales, purchases, customers, payments, reports and users, plus `audit.read`. Future modules must require these permissions server-side; declaring a permission does not create its endpoint. Owners and super administrators have every permission. Managers have operational permissions but no business-settings write or user management. Cashiers have catalog/stock reads, sales/customer/payment operations, and no stock write or role management. Viewers retain organization/location reads. Custom roles use an explicit allowlist; membership delegation cannot be assigned as a custom permission. Unknown roles deny everything.

Business scope covers its resources. Store scope includes its warehouses and terminals; warehouse scope includes only that warehouse and its terminals, plus the parent store as read-only context. Parent state must be active. Business-level settings and membership reads cannot be granted to a scoped custom role. Location lists and ID-based operations enforce these restrictions on the server. Audit rows carry store/warehouse scope; scoped reads exclude business-wide/legacy events rather than exposing their contents. Audit data uses an allowlist that omits contact details, tokens and passwords; updates/deletes are rejected by database triggers and have no API routes.

Platform administrators are separate from business memberships. They can explicitly access every business; no client flag or membership payload can grant the role. Bootstrap/revoke is an operator-only CLI with existing database credentials:

```sh
npm run build -w @inventory/api
# Feed JSON on stdin: {"action":"grant" or "revoke","actorId":"operator-account-uuid","accountId":"target-account-uuid"}
node --env-file=apps/api/.env apps/api/dist/auth/platform-admin-cli.js
```

Both accounts must be active. The operator is trusted at the database boundary; actor attribution is supplied by that operator, not proof of browser authentication. Changes append protected platform audit and revoke the target's existing sessions. This CLI is deliberately unavailable through tenant APIs. Operators inspect global platform audit through controlled database administration; application audit screens show authorized business history only.

Down migration removes scope/custom permission data and maps cashier/custom memberships to viewer, never owner. This is a lossy downgrade: back up before production rollback and prefer forward fixes. RLS remains explicitly deferred as documented in organization management; all new domain operations must use authenticated scoped transactions.

Impact: auth/global-role persistence → scoped organization transaction → API contracts and portable permission presentation → web/Tauri and native mobile. No new local persistence, offline grants or sync bypasses. UI checks do not replace server authorization. Account/session rechecks and stale-response clearing remain in place.

Validation: PostgreSQL suite passed 20 tests including role escalation, cross-business and cross-store denial, scoped manager audit/location access, cashier/custom restrictions, server-derived platform role and audit immutability. Three migrations applied, repeat-up applied zero, rollback passed. Full validation passed: 48 unit/component tests, 12 tooling tests, lint/boundaries/types, API/web builds, real Chrome management/axe checks and Android/iOS/web exports.

## 3. Catalog

Implemented `apps/api/src/catalog`, shared catalog contracts/client and web/mobile catalog forms. Products have server UUID identity, business-unique SKU/identifier registry, category, descriptions, up to five HTTPS image references, barcodes/alternate codes, type, tracking flag, status, UTC creation time and optimistic version. Services cannot track stock. Archived products retain their identifiers and cannot be restored. Stock quantities are not product fields and payloads attempting to set them fail strict validation.

Category parents are business-bound; cycles, duplicate sibling names, and deactivation of categories with active dependents fail. Product queries have stable pagination, status/category/type filters and exact code lookup. Catalog metadata is business-wide: scoped operational roles may read it, while editing business-wide product identity requires business-wide scope plus products.write. No warehouse or store scope grants access to another business.

Web/Tauri support keyboard-wedge barcode scanners in the code field. Android/iOS implement an opt-in Expo Camera scanner with explicit camera permission, cancellation and manual entry fallback. Expo web uses keyboard/manual entry. Only the scanned code reaches the lookup API; no images are uploaded. `expo-camera` matches Expo's bundled SDK version. Camera permission/physical hardware behavior still needs native device qualification. Product images are owner-supplied HTTPS references; upload/object-storage and import/export adapters did not previously exist, so no fake upload/import endpoints were added.

API/DB tests cover duplicate codes, pagination, barcode search, category cycles/foreign parents, quantity-field rejection, scoped write denial and irreversible archival. Web/native form tests exercise creation without quantity editing. Stage validation passed: 55 unit/component tests, 25 PostgreSQL integration tests, API/web builds, Expo Android/iOS/web exports, and real Chrome category/product creation, barcode lookup, status editing and axe checks.

## 4. Variants, units and pricing

Products now have a default Each-unit variant; additional variants carry attributes, distinct SKU/barcodes, base unit, purchase/sale/count units, cost/currency and state/version. Named units have dimensions, and per-variant direct conversions are positive, immutable and dimension-compatible. The base unit cannot change after creation; add a variant with the correct base unit instead of reinterpreting history. Add conversions before selecting non-base operational units. Product default identity stays synchronized while separate variant identifiers are preserved.

`PricingService.quoteInTransaction` is the single authoritative pricing entry point for current quotes and future final-sale validation. It rechecks product/variant/store availability and caller scope, converts to base quantity exactly, chooses the most recently effective store price before a business price, then selects one eligible promotion by priority, store specificity and stable ID. Promotions never stack; an authorized larger manual discount replaces the promotion. Warehouse-scoped managers cannot override store-wide discounts. Cashiers cannot override discounts or see cost information. Cost changes require purchasing write permission.

Price records are immutable historical versions. An effective end is exclusive; when a newer bounded price expires, the next eligible older price is the documented fallback. Duplicate effective starts in the same variant/store scope fail. Promotions can be withdrawn with a separate immutable record. Quotes return applied price/promotion IDs, currency, exact base quantity and rounded net/tax/total minor-unit strings. They are not completed sales and must be recalculated in the final transaction when sales are implemented. No fake checkout endpoint exists.

Web/Tauri and mobile provide variant/unit/conversion forms, price and promotion publication/withdrawal, and server quote previews. Common field descriptions are portable application metadata; controls remain platform-native. User-facing percentages are converted exactly to basis points. Tax-exclusive quotes round net and tax at line currency boundaries; inclusive quotes round total/net and derive tax by difference. The quote total is the sum of rounded components.

Customer-specific pricing is not enabled because the repository has no authenticated customer identity/assignment model; accepting an arbitrary customer ID for a discount would be unsafe. The user requested this where relevant; current pricing is business/store-specific. There is no implicit FX conversion. Supplier purchase documents in step 6 will preserve their own agreed currency/unit costs.

Step validation: 56 unit/component tests and 29 PostgreSQL integration tests passed, including default-variant migration, duplicate attributes/codes, incompatible conversions, price precedence, promotions, protected costs, immutable records and withdrawal. Chrome pricing publication/quotes/promotion withdrawal and Expo Android/iOS/web exports also passed.

## 5. Inventory movement ledger

`inventory/LedgerCore` is the only stock mutation interface. Every entry stores a stable UUID, ordered sequence, business, variant, warehouse/location, signed deltas, actor, reason, source and command identity. PostgreSQL prevents movement updates/deletes. Manual corrections append a unique linked reversal; purchasing and transfers require their own compensating workflows. Opening stock is accepted only before any history exists for that stock key. Product forms cannot overwrite balances or change inventory tracking after history exists.

On hand is physical quantity including damaged units. Available = on hand − reserved − damaged. In transit is dispatched quantity outside source/destination physical stock. Reservations do not change on hand; release/consumption changes their remaining projection and ledger atomically. Manual reservations persist until explicit release; there is no implicit timeout that could invalidate a transfer. Negative stock defaults off; only business settings permission can change it, and disabling it with negative balances fails. Transfers/bin moves require physical availability even when negative stock is allowed.

OrganizationScope serializes each business before fresh authorization; LedgerCore additionally locks balance rows. Movement, projection, audit, business document and operation receipt commit together. Reconciliation compares summed ledger deltas with balances and active reservation totals. A mismatch is an investigation result, never an automatic overwrite. Archived products, variants, businesses, warehouses and storage locations cannot hide nonzero stock. Inactive catalog/locations must be reactivated before posting further movements.

Web/Tauri and native mobile expose stock history, paginated item/balance lists, opening/receiving/sale/return/adjustment/damage facts, manual reservations/releases, reversals, policy and reconciliation. A manual sale movement records an inventory fact only; it is not checkout, a payment or a financial sales document. Client command keys survive uncertain retries in memory. After reload/sign-out, inspect document/history before issuing a new uncertain command; there is no durable offline outbox.

Step validation: 59 unit/component tests, 34 PostgreSQL integration tests, API/web build, and real Chrome opening/reservation/release/reconciliation passed. Tests cover duplicate commands, competing deductions, negative-stock policy, rollback after a forced projection failure and append-only history.

## 6. Suppliers and purchasing

Business-owned suppliers have code, name, contact fields, notes, status and optimistic version. Profiles are shared within their business; purchase readers may see contacts, while profile changes require business-wide purchasing write authority. Orders are warehouse-scoped and retain supplier, currency, reference, actor, UTC creation, version and immutable ordered unit/base quantities and costs. Draft orders accept up to 50 lines; additional lines can be added in the screens. To replace an incorrect draft, cancel it and create a corrected reference. Approval locks lines; ordering permits receiving.

States are draft → approved → ordered → partially_received → completed. Cancelling draft/approved/ordered/partial orders closes outstanding backorders without removing already received stock or costs. Completed orders cannot be cancelled. Receipts are positive quantities in the ordered unit, converted using the historical order ratio. Inexact six-decimal conversions and excess deliveries fail. Receipt UUIDs link immutable purchasing records to `purchase_receive` ledger movements. Returns reference a real receipt, cannot exceed its unreturned quantity, and post `purchase_return` movements at the original receiving location. Move goods back there first if they were put away elsewhere. Returns preserve the original received history and do not silently reopen an order.

Invoices are immutable supplier invoice/payable references with positive exact minor-unit amount, order currency and due date. They remain explicitly **unallocated**, because payment settlement, credit valuation, tax invoice generation and full accounting were not requested. Return credit references are traceable references, not fabricated paid credits. No mutable supplier balance is invented. Purchase history supports supplier filters, reference search, pagination and order receipt/return/invoice detail on web/Tauri and native mobile.

Step validation: 36 PostgreSQL integration tests and the workspace validation passed. Purchasing tests cover approval, draft line locking, partial/complete receipt, concurrent retry deduplication, excess returns, cancellation, preserved costs, unauthorized reads and ledger reconciliation.

## 7. Hierarchical storage

The inventory migration introduced a warehouse root only where required for stock. The storage migration extends it with optional zone, aisle, rack, shelf and bin levels. Levels can be skipped; parents must rank above children within the same warehouse/business. Database triggers and compound foreign keys reject cycles, invalid parent/type edits and active children beneath inactive parents. Codes are unique within a warehouse. Capacity and its explicitly named unit are descriptive metadata, not a promised volumetric enforcement engine. Notes and up to five HTTPS photo references are optional; no upload service is fabricated.

Stock balances already key by location. Warehouse totals sum those location projections; there is no independently editable warehouse quantity. A location move appends outgoing/incoming ledger records in one idempotent transaction and requires available undamaged source stock. Nonempty locations and parents with active children cannot be deactivated. Roots are managed through warehouse lifecycle rather than relabelled into bins.

Screens support warehouse/search selection, paginated locations and warehouse totals, location creation/editing, stock movement and Code 39 labels encoding the uppercase location UUID. Optional API filters include type/state. Label rendering shares portable bar geometry; DOM uses SVG and native uses Views in a horizontal scroll region. The standard symbol values were cross-checked with [ZXing's Code39Reader](https://github.com/zxing/zxing/blob/master/core/src/main/java/com/google/zxing/oned/Code39Reader.java). Actual camera/printed-label scan quality still requires hardware qualification; manual IDs and codes remain available. Use inventory history/balances for location-specific quantities.

Step validation: 60 unit/component tests, 37 PostgreSQL integration tests and workspace validation passed. Tests cover parent cycles/ranks, duplicate codes, active descendants, nonempty deactivation, repeated moves, excess moves and warehouse/location reconciliation.

## 8. Transfer lifecycle

Transfers bind approved locations in one business. Both source and destination must be inside the caller's authenticated scope. This intentionally requires a business-wide operator for cross-store moves and a store-wide operator for cross-warehouse moves within that store; a warehouse-scoped actor can operate between its own bins. The same rule applies to listing, detail and receipt confirmation. Cross-business IDs fail; commercial inter-business trade requires a future independently authorized sale/purchase workflow.

Drafts contain up to 50 distinct variant lines and immutable unit-conversion snapshots. Approval reserves source quantities. Dispatch consumes those reservations and posts source physical deductions plus in-transit additions. Draft/approved cancellation releases any holds atomically. Cancellation after dispatch is rejected: settle receipt/discrepancy instead. Every transition uses optimistic versions, current authorization and an idempotency receipt.

Destination receipt quantities are explicitly base-stock units. Partial receipts reduce source transit and add destination physical stock; damaged receipts also increase destination damaged stock. Explicit confirmed shortages reduce transit without creating destination stock and preserve actor/reason in immutable receipt/event history. A line cannot settle more than dispatched quantity. Total physical plus in-transit stock is conserved except for separately recorded losses. Receipt, both ledger sides, projections, document state, audit and replay response share one transaction. A forced destination failure rolls the source side back. The transfer becomes completed only when every dispatched base quantity is settled.

Web/Tauri and native mobile expose draft creation/additional lines, approval, dispatch, partial destination receipt, discrepancies, cancellation and actor/time history. Core transfer tests cover competing consumption, retries, cancellation, cross-tenant rejection, damage/loss, excess receipt and rollback. Final validation and platform qualification are recorded below.
