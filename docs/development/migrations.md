# PostgreSQL and migration workflow

The API uses `pg` with a bounded pool, connection/query timeouts and graceful pool shutdown. `node-pg-migrate` manages ordered SQL migrations under `apps/api/migrations`. No ORM or startup auto-migrations exist. Authentication, organization and authorization tables are implemented; subsequent domain schema follows [data/API conventions](data-api-conventions.md). Readiness executes `SELECT 1`; it does not prove future schema-version compatibility.

1. Provision a development database and role. Copy `apps/api/.env.example`, then set `DATABASE_URL`. Do not place credentials in shell history, documentation or committed files.
2. `npm run db:create -w @inventory/api -- meaningful-name` creates an SQL migration template. Fill forward SQL and a safe reversal where possible; remove placeholder statements before review.
3. Review locks, data backfill, indexes, tenant constraints and compatibility with deployed clients. Prefer expand/migrate/contract changes. Run against a disposable database first.
4. `npm run db:migrate -w @inventory/api` applies pending migrations under the migration runner's lock and a transaction. Running it again must make no changes. With no migrations, only runner metadata may be initialized.
5. `npm run db:migrate -w @inventory/api -- down` rolls back one migration in non-production only. Production repairs use a reviewed forward migration with backup/recovery planning.

Production environment requires `DATABASE_SSL=verify-full`; certificate verification is never disabled. The URL must not contain TLS query overrides; use an appropriate trusted CA through Node's supported trust configuration when needed. Run migration commands under a separate schema-owner role, and the API under a least-privilege runtime role. No automatic schema sync or superuser runtime connection.

The migration script loads `.env` relative to the API workspace through Node's environment-file option. Configuration validation uses the same parser as the server. Errors omit credentials and SQL contents. For investigating failures, inspect local reviewed migration files and controlled database logs; never dump the entire environment.

Every schema task must test clean installation, upgrade from the preceding schema, repeat migration runs, constraints and rollback/forward recovery against real PostgreSQL. Local IndexedDB/SQLite schemas need separate versioned migration adapters that preserve unsent operations; central SQL migrations cannot substitute for them.

## Deployment and transactions

The workspace migration command builds the API first. The runner and CLI compile to JavaScript in `dist/database`; no TypeScript loader is needed in production. `npm run package:api -- artifacts/api-release` includes SQL migrations in the API-only artifact. Within that artifact, install with `npm ci --omit=dev`, inject production configuration, then run `npm run db:migrate` once as a release job before `npm start`. The artifact command forces production policy; it does not load local env files. API startup never runs migrations. Advisory locking, migration ordering and a single transaction are enabled. Nontransactional SQL (such as concurrent index creation) requires a separately reviewed approach; do not disable atomicity casually. The configurable statement timeout also applies to migrations; tune it for reviewed operations.

Application services own transaction boundaries using `DatabaseService.transaction(async (transaction) => ...)`. Pass this scoped query interface to participating repositories, and await every query. All work uses one checked-out connection. Success commits; failure rolls back; a failed rollback discards the connection. The interface rejects queries after its scope ends. Do not use the pool directly inside a transaction, nest transactions, manually commit, or make external network calls while holding locks. Use bound values (`$1`, etc.); identifiers must come from trusted allowlists. PostgreSQL's default READ COMMITTED isolation applies. A feature needing stronger isolation or explicit row locks must specify and test it. Do not automatically retry ambiguous commits or non-idempotent work. External effects need a feature-specific post-commit/outbox design when required; the existing offline sync uses durable operation receipts and separate local encrypted outboxes.

The eight-command domain rollout adds migrations through `1793300000000_transfers.sql`. That historical rollout had ten migrations; the current total is 23 (see the migrations README). Fresh install, repeat-up and all down migrations passed on disposable PostgreSQL 18. Existing catalog products are backfilled to default variants and warehouse roots; no balances are invented. Purchasing/transfer ordered quantities and costs are protected after approval; movements, receipts and protected events remain append-only. See [rollout and recovery limits](domain-rollout.md#impact-and-deployment) before applying these migrations to existing application data.
