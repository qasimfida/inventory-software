## Implemented capabilities

- Typed preference schemas and one portable resolver distinguish defaults, user choices, business enforcement, platform enforcement and local accessibility/capability constraints. OS reduced motion and low-power constraints can reduce effects; no presentation setting changes authentication or offline authorization. Unknown writes fail validation; legacy invalid preferences fall back per field. System fonts are the only implemented font option.
- PostgreSQL stores preferences by the authenticated account, never by a supplied user ID. Policies use platform/active-business scopes. Versioned replacement rejects stale writes. Administrators with business.write (including owners and platform administrators) manage business policies through OrganizationScope; only active platform administrators manage global policies. Policy audit events retain typed before/after values.
- Web/Tauri and native clients share settings and security models with stale-response guards; each owns its controls and theme adapter. Preferences persist on the server across sessions/devices. Guest appearance is temporary. Offline startup uses safe defaults until authenticated settings load; no sensitive policy or session authorization is cached in browser storage. Settings mutations are online-only and single-attempt.
- Appearance supports light/dark/system, default/teal accents, compact/comfortable spacing, three text sizes, motion limits, state presentation and optional effects. Native text respects OS scaling. Compact web spacing cannot reduce interactive target size. Visualization detail is a typed preference for applicable consumers; no chart/map/3D feature or asset was introduced.
- Readiness probes verify the configured API and database every 30 seconds. The existing encrypted offline register exposes durable outbox, retry/conflict status and bounded permission. No connectivity toggle can grant offline rights or create a LAN gateway.
- Server-side installation recognition links sessions to account-specific device records. Browser markers use a separate HttpOnly/SameSite cookie (Secure and `__Host-` in production). Native markers use origin-scoped SecureStore; Tauri stores only a non-secret random installation marker in origin-scoped WebView localStorage. Session tokens remain memory-only on desktop and HttpOnly in browsers. Signals are hashed in PostgreSQL and never accepted as credentials. Missing/reset markers create a new-device event; simultaneous logins serialize on the account.
- Successful/failed logins, new devices, session renew/revoke, recovery issuance/completion, sensitive settings and credential rate-limit thresholds have a separate append-only security trail. Existing role, stock and financial audit/ledger records are reused. Update/delete/truncate triggers protect security records; truncate protection also covers existing organization/platform audit tables. Privileged database owners can still disable triggers; this is application-level immutability, not a cryptographic claim against database administrators.
- New-device notifications are transactionally queued for the affected user, active business owners in each applicable tenant, and active platform administrators according to policy. The worker claims bounded batches, durably records attempts, applies exponential backoff, stops after eight failures and exposes explicit administrator retry. A unique durable inbox entry makes retries idempotent. `delivered` means insertion into this application's inbox committed; it never means email/SMS/push delivery. Membership/account/platform-role access is rechecked at inbox read/acknowledgement time.
- Unexpected HTTP failures produce allowlisted diagnostics with environment, configured application version, safe code/category/reason/recovery, feature, severity, correlation ID and authenticated actor reference. Client failures expose the safe correlation reference. Expected validation/security rejections are structured log events, distinct from unexpected-error storage. No raw request, URL, credential, SQL or exception message/stack is stored. Platform-admin access protects diagnostic reads.

## Configuration and connectivity

Apply migrations 20–21 before the updated API starts: `npm run db:migrate -w @inventory/api`. These additive migrations add settings, devices, security events, delivery/inbox and diagnostic tables plus nullable session device references and historical audit session IDs. It does not reset users or alter business ledgers. Set server `APP_VERSION` to an immutable build/release identifier (default `0.0.0`). No new client secrets or notification credentials are required for in-app delivery.

Cloud/online clients use the configured API origin. Offline capabilities remain those in [synchronization](../offline/synchronization.md): cash-only authorized capture, bounded grants, encrypted local data, durable outbox, server idempotency and explicit conflict review. Settings and policy updates never enter the financial outbox.

A single-authority LAN deployment can reuse the same Nest API and PostgreSQL on an operator-managed local server. It requires a trusted HTTPS reverse proxy/certificate, reachable DNS/static address, firewall controls, verified PostgreSQL TLS, explicit allowed browser origins, and each application's configured API origin. Desktop releases must include that exact origin in their CSP; native devices must trust the certificate. Ordinary account/session/membership permissions remain mandatory. Do not expose the development server/database or dev seed accounts to a shared network. All clients must use one authority; changing origins partitions credentials and offline vaults. There is no peer discovery, gateway provisioning, multi-server/cloud replication or offline merging between independent servers. These deployment components and physical LAN qualification are not installed here, so the API reports `localNetwork: deployment-required` rather than advertising a tested local-network mode.

Notification providers: only the durable in-app inbox is implemented. Email/SMS/mobile push require an approved provider, server-side credential injection, recipient verification and a reviewed idempotent delivery adapter. They are not configured or simulated. MFA/passkey enrollment/recovery remains absent; new-device detection does not replace MFA. Privileged MFA and the existing Expo dependency advisories remain production release risks.

## Access and retention

Open **Settings, connectivity and security** after sign-in for account preferences, readiness, security inbox and personal security events. Platform administrators additionally see platform policy, restricted diagnostics and pending/failed notification delivery with retry controls. Business owners use **Business policy** in the selected workspace. Account controls list device references for active sessions and revoke one/all sessions. The existing business audit screen remains authoritative for memberships, inventory and financial activity.

Unexpected diagnostic rows expire after 30 days, in bounded worker cleanup batches. Security events, existing ledgers/audits, device references and associated notification records have no automatic deletion in this foundation. Production operators must define archival/access controls and monitor growth; no ordinary API can modify/delete the audit trail. Restrict structured stdout to operators and apply 30-day log rotation in the deployment collector. The application cannot configure an external log collector. Use separate migration/runtime database roles; runtime must have no DDL, trigger-disabling or audit UPDATE/DELETE/TRUNCATE rights. Preserve database backups and external audit exports if protection against privileged database changes is required.

Guidance checked during the implementation: [OWASP logging](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html) and [session management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html). These informed event separation, allowlisted metadata and retention/access controls; the implementation does not claim formal compliance.

## Remaining qualification and limits

- Windows native builds, installed Android/iOS tests, physical-device SecureStore/SQLite, native macOS WebView behavior, signing/notarization and physical LAN deployment remain unverified. Browser bearer simulation is not native verification.
- Privileged MFA/passkey enrollment and recovery are not implemented. The 22 Expo dependency advisories remain a release blocker; the isolated API artifact's clean audit does not clear the full monorepo. See [Stage 4 advisory details](stage-4.md).
- Notifications are confirmed **in-app** delivery only. No email/SMS/push provider is installed. No automatic LAN discovery, gateway provisioning, independent-server replication or multi-authority inventory merge exists.
- Server/API diagnostics persist for 30 days. Client-only transport/offline failures retain their existing safe workflow/outbox status; no external browser/native crash-reporting service is configured. Durable security/audit retention requires a deployment archival policy and restricted database/log administration.
- UI settings persist on the server; offline startup uses safe defaults until authentication/settings load. Unsupported stylistic fonts, charts/maps and 3D capabilities are not downloaded or presented as implemented features.
- Six pre-existing source-size warnings remain. Vite reports its existing future config-loader warning and a **505.73 kB minified / 154.39 kB gzip** entry chunk warning; builds pass. No warning threshold was raised to hide these.
