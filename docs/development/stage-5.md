# Stage 5 — reports, profiles, notifications and warehouse hierarchy

## Inspection and impact map

Existing transaction services, exact-money subledgers, immutable stock movements, scoped authorization, settings CAS versions, security diagnostics and durable notification delivery are retained. No report module existed. Purchase/transfer approval and stock-count review already exist; these remain the authoritative commands. Storage has hierarchical locations but no surveyed coordinates, dimensions or cost-of-goods snapshots.

| Layer               | Existing ownership                                         | Stage 5 change                                                                                                                    |
| ------------------- | ---------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| Domain/transactions | sales, purchasing, payments, LedgerCore, counts, transfers | Read-only reconciled reports; transactional notification enqueue on relevant audit events; existing approval commands reused      |
| Schema/security     | OrganizationScope, immutable audit, migrations 1–21        | Scoped report indexes and durable business deliveries; current permission checks on every read/action                             |

## Plan and acceptance

1. Add permission-specific aggregate reports and paginated inventory/movement summaries, preserving exact decimal strings and separate currencies. Period flows use inclusive UTC calendar dates (maximum 366 days); balances are explicitly current.
2. Extend established settings with schema-versioned general/retail/wholesale profiles and a default low-stock threshold in each SKU's base units. Presets are presentation conventions, not unimplemented regulated workflows.
3. Extend durable in-app delivery to business audit events with role/scope revalidation. Present existing pending approvals and invoke existing idempotent commands after review.
4. Provide optional lazy hierarchy navigation with real per-location stock and a list fallback. This is a schematic hierarchy, not a physical floor plan. Defer 3D: no geometry, demonstrated additional value or renderer exists.
5. Run migrations, focused and full regression checks, supported builds; record actual outcomes below. No Stage 6 changes.

## Implemented behavior and limits

### Reports (Command 26)

`GET /api/v1/businesses/:businessId/reports` accepts `section`, inclusive UTC `from`/`to` dates, optional authorized `warehouseId`, `offset` and `lowOnly`. Date spans are ordered and limited to 366 days; pages contain at most 50 measures. `reports.read` is necessary but never sufficient: sales additionally needs `sales.read`, purchases `purchases.read`, payments `payments.read`, receivables `customers.read` plus `payments.read`, payables `purchases.read` plus `payments.read`, and inventory/movements `stock.read`. Supplier payment measures also require `purchases.read`. Warehouse/store constraints come from fresh authenticated membership context on every query, including when the warehouse filter is absent.

Sales report gross completed transactions, returns/voids on their own posting dates, net revenue excluding tax after returns, and transaction counts. Purchase reporting distinguishes posted invoice/credit values from order estimates and counts receipt lines/order states. Cash payments exclude change and include linked refunds. Current AR/AP derives from immutable obligations minus allocations/credits/settlements; a negative net payable means a supplier credit balance. Currencies remain separate, with explicit minor-unit labels; SQL numeric results remain strings through the client, avoiding JavaScript precision loss. No profit, inventory valuation or margin is claimed: the current editable variant cost is not a historical COGS allocation.

Inventory summarizes recorded stock keys by SKU/warehouse/base unit, with on-hand, reserved, damaged, in-transit and available values. Products never stocked in a warehouse are not presumed to have a zero balance there. Movement opening + period change = closing comes directly from the immutable ledger. Current stock and outstanding balances are explicitly independent of the selected report dates. The existing movement-history and reconciliation endpoints remain authoritative for individual references and projection checks. There is no cached offline financial report, arbitrary query builder, export service or accounting/general ledger.

### Industry profiles (Command 27)

Business policies now optionally contain `industry: { schemaVersion: 1, kind: 'general' | 'retail' | 'wholesale', lowStockThreshold: string }`. They use the existing policy CAS version and `business.write`, retain appearance/enforcement settings, and are included in both organization and security audit records. Platform policies reject industry profiles. Business settings show the preset's customer/purchasing terminology; these are conventions, not separate domain implementations. The threshold defaults to zero and supports six decimal places in each SKU's base units. It applies to low-stock reports, warehouse availability crossings and local-location indicators. Changing a threshold does not emit historical notifications; inspect the low-stock report to identify already-low stock.

No unrequested custom-field engine, regulated pharmacy/medical compliance, restaurant preparation, expiry/lot/serial workflow or industry-specific tax calculation is introduced. Those options are unsupported. Cash remains the only external settlement method.

### Notifications and approvals (Command 28)

`OrganizationScope.audit` calls the notification module's transaction function after writing the immutable event. Relevant purchase creation/approval/cancellation, manual stock adjustments, supplier returns, transfer lifecycle, count submission/approval, sale return/exchange/void, low-stock crossings and business-policy changes enqueue deliveries for active members whose current permissions and location scope match. Notification policy's existing `notifyBusinessAdmins` flag now controls operational business delivery to eligible roles as well as owner new-device alerts; platform policy retains precedence. Account/new-device alerts retain their separate existing security inbox. Platform administrators without a business membership are not automatically subscribed to every business's operational events.

Migration 22 adds a durable queue with a composite tenant/audit reference, recipient uniqueness, scope constraints and due/recipient indexes. The existing lifecycle worker calls a shared delivery routine for both security and business queues: 25-row `SKIP LOCKED` claims per queue, persisted attempts/30-second lease before I/O, exponential backoff capped at one hour, eight attempts, terminal interruption handling, and owner-authorized audited manual retry. In-app delivery is marked complete only when its database transaction commits. Restart and concurrent workers cannot create duplicate inbox rows. Delivery, read and failure status are distinct; no email/SMS/push delivery is claimed. Queue records and audit records require a deployment retention/archive policy.

Every inbox read/read-ack revalidates recipient, membership, account/business state, permission and current store/warehouse scope. A notification carries an event/resource reference, not financial payloads or authority. Approvals query current purchase/transfer drafts and submitted counts; approved items disappear from that queue. Review screens fetch the actual document, show quantities/costs or discrepancies, require a reason and invoke the existing versioned/idempotent domain commands. The server rechecks authorization and stock. Original semantics remain: purchase/transfer write permission permits approval; count approval requires `business.write`; there is no new mandatory two-person rule or staged approval requirement for every adjustment/return. Existing uncertain-command policy remains: after closing/reloading an ambiguous command, inspect current document history before retrying.

Review also found that purchase approvals accepted a reason without preserving it in the organization audit projection. Purchase, count and transfer approvals now retain an allowlisted `approvalReason`; a real database regression verifies that a duplicate approval produces one audit record with the original reason. Generic free-form metadata remains excluded.

### Warehouse visualization (Commands 29–30)

`GET /businesses/:businessId/warehouse-view` requires `stock.read` and an authorized warehouse. It returns only the selected real node, up to 50 children, and up to 50 stock keys, with independent pagination. A warehouse without a storage root row is represented by its actual warehouse identity, as in the existing storage API; no stock or coordinates are invented. Web/Tauri offers a table and optional CSS hierarchy cards when enhanced visualizations are enabled. Native uses an accessible navigable list. Parent/root controls and stock values remain usable without graphical presentation. Low indicators on this screen apply to the selected location, whereas low-stock alerts/reports use warehouse totals.

3D is deliberately deferred. The database has no surveyed coordinates, dimensions, collision/access paths or defined operational task that benefits from depth rendering. No engine/assets are downloaded and POS remains independent. A physical 2D floor plan likewise requires measured geometry; the implemented view is explicitly a hierarchy schematic.

## Performance and deployment

All web business sections now use React lazy imports and Suspense; report/inbox/hierarchy modules are evaluated when opened. The existing service worker still precaches static chunks in the background for shell recovery, so lazy execution is not a claim that production downloads exclude those chunks. There are no chart, 3D, provider or other new dependencies. Reports use indexed, bounded aggregate queries and 50-row result pages; they reuse the existing serialized business transaction and database statement timeout. Large historical ledgers can still make an all-history opening balance expensive; production-scale load testing and a validated period snapshot strategy are future capacity work, not an unverified performance claim. Current stock reports are not periodically polled. Native report/inbox/hierarchy queries wait until their section is opened.

Apply `npm run db:migrate -w @inventory/api` before starting the updated API. Migration 22 adds queue/index structures only; no business stock/financial data is rewritten. Existing completed workflows and bounded offline sales remain unchanged. No provider credentials are required for these in-app features. External notifications, surveyed warehouse geometry and historical valuation require separate setup/design. Existing Stage 4/25A release blockers (MFA, mobile-tooling advisories, native device/Windows qualification, LAN provisioning) remain separately documented.
