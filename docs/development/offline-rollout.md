# Offline, live updates and warehouse workflow rollout

The five requested stages are implemented in sequence: durable offline storage/synchronization, offline cash checkout, live invalidations, controlled counts, and integrated warehouse scanning. Cash remains the only payment method. Existing unrelated workspace changes were preserved.

## Ownership and changes

| Layer                     | Changes                                                                                                                                                                                                    |
| ------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| PostgreSQL/API            | Three migrations: durable revision feed/cursors/leases/operation receipts; stock count sessions/lines; damaged purchase receipts. Business-scoped authorization and transactions remain authoritative.     |

## Stock counts

Counts belong to one authenticated business, warehouse and root or explicit location. Their explicit variant scope is bounded to 100 variants; missing products are never inferred as zero. Count sessions and partial observations persist on the server and can be resumed. Barcode/SKU/variant lookup resolves the product and available units; carton conversion uses the catalog's exact conversion rule. Saving a count replaces the selected line's absolute total rather than incrementing it for repeated scanner events. Zero is an explicit valid count.

Blind draft responses hide expected quantities. Submission requires every scoped line to be counted and exposes the discrepancy for review. Blind presentation does not revoke any separate inventory-read permission the operator already possesses. `stock.write` permits capture/submission/recount; `business.write` permits approval. Owners can perform both stages, but approval is a distinct audited command; this is not a mandatory two-person approval policy.

Each line snapshots on-hand quantity and balance version when its session begins. Any intervening movement, even a movement later reversed, makes approval fail. A full recount refreshes the cutoff and clears current quantities while retaining attempt numbers and audit events. Approval checks every version in the business transaction and posts exact differences through LedgerCore. Reserved/damaged stock invariants can block an adjustment; they are never silently discarded. Retries return the same receipt, approved sessions cannot be edited, and stock ledger reconciliation remains available.

The UI lists the latest 100 sessions for the selected warehouse; individual IDs remain addressable through the scoped detail API. JSON exports include the scoped session, current observations, operator/timestamps and review state; blind draft exports also hide expected stock. Capture/recount/approval audit events are available in the existing audit screen.

## Warehouse scanning

The workbench resolves product barcodes, SKUs or variant IDs and active destination/source location codes or IDs within the selected warehouse. USB/Bluetooth keyboard wedges act as text input without a device SDK. Native mobile reuses Expo Camera; unsupported camera environments retain manual/keyboard entry. A scan selects context and never posts inventory. Duplicate camera callbacks are suppressed; posting requires an explicit confirmation.

Purchase receipt forms validate the selected product and **ordered unit** against the purchase line, show ordered/already-received quantities, and support partial receipts. Damaged quantity is included in total received quantity, recorded in the immutable receipt with reason/operator/time, and applied to the damaged balance in the same ledger transaction. Unknown products/units or locations are rejected. Unexpected goods must remain physically quarantined while purchasing amends and approves the order; the application does not manufacture an unapproved receipt. Returning a receipt containing damage currently requires supervised reconciliation and is blocked by the ordinary return endpoint.

Location moves use the existing paired ledger movements. Transfer dispatch validates the source and dispatches **all approved lines**; it is not a per-item partial dispatch. Transfer receipt validates destination and line/unit, supports partial good/damaged/shortage settlement, and retains existing workflow history. Permission, conversion, remaining quantity, capacity, reservation and stock rules remain in the owning services.

Warehouse posting and count capture are **online only**. Only cash-sale replay has been approved for offline operation in this implementation. Server-persisted count drafts resume after interruption. In a live warehouse confirmation, retries retain the command key; after a hard reload or lost in-memory command state, inspect document/movement history before entering another receipt. The UI does not promise offline warehouse posting or durable local warehouse drafts.

## Live updates

There was no established socket stack. Authenticated three-second revision polling supplies scoped invalidation hints, while durable delta cursors supply recovery. Product/price/stock and operational changes are recorded transactionally. Online POS invalidates quotes and requires recalculation/review; open scanning workbenches display a refresh notice. Duplicate notifications never execute business commands. Offline registers pull independently and retain original sale price facts; scheduled price transitions are detected at minute granularity. Current server pricing is still checked synchronously at online checkout.

## Deployment and operational limits

Apply all 17 migrations through the existing migration command before running updated clients. Validation uses disposable PostgreSQL databases; it does not upgrade the developer's existing application database. The API remains independently deployable. Rollback testing is for development: posted stock/financial history must be backed up and reconciled before any production rollback. The count downgrade retains immutable movement origin strings, matching the existing sale migration convention.

Offline data is partitioned by API origin and then named vault, with business/account/device identity inside the encrypted document. Do not change API environments or clear storage while work is unresolved. The initial snapshot limit is 250 active variants, one currency and root-warehouse stock. The outbox retains up to 1,000 records without automatic purging. Encrypted backup/restore APIs exist for support integration; an end-user backup UI, automatic off-device backups and a production retention/restore-drill process are outstanding operational work.

Windows build/runtime, installed iOS/Android SQLite and background behavior, physical scanner/camera devices, and physical printers remain unverified in this host environment. Native exports and adapter SQL tests are not a claim of installed-device certification. The macOS bundle was built here; release signing/notarization and Windows packaging require their normal host/credentials. Expo web has IndexedDB but no offline-reload shell; use the primary production web build for that capability.

The two scanning shells have reviewed source-size exceptions alongside four existing exceptions; count state and controls were extracted into separate components. Six max-lines warnings are expected. Browser bundle-size and experimental Node SQLite test-runner warnings, if emitted, do not represent runtime test failures.
