# Authentication, sessions and recovery

## Scope and impact

Invitation-only onboarding suits staff access to this product. Authentication establishes an active account identity; business routes additionally enforce tenant/resource permissions. Stage 4 adds operator-issued password recovery using the existing identity model. Public staff registration, automated email delivery, MFA enrollment and external identity-provider integration remain absent. Guest storefront access is a separate approved design, not an implemented staff-registration exception; see [Milestone 1 D06](../decisions/milestone-1.md#d06--public-and-guest-api-boundaries). The Command 6 validation section below is historical; see [Stage 4](../development/stage-4.md) for current evidence.

| Layer                   | Implementation                                                                                                                                                         |
| ----------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| API owner               | `apps/api/src/auth`: controller/DTOs, application service, session repository, global guard, abuse limits, password/token utilities and operator CLI                   |
| Database                | One ordered migration creates accounts, invitations, sessions and rate-limit buckets; foreign keys and transactional invitation consumption prevent partial onboarding |
| Shared contracts/client | `packages/contracts/src/auth.ts` validates responses; `packages/api-client/src/auth.ts` injects transport/storage and serializes renewal with other session operations |
| Web/macOS/Windows       | DOM account panel; browser HttpOnly cookies; isolated platform selector uses an ephemeral memory credential store in Tauri                                             |
| Android/iOS             | Native account panel; Expo SecureStore adapter; lifecycle checks lock on background/resume                                                                             |
| Expo web                | `.web.ts` storage adapter selects cookies; native secure-store implementation is not bundled into the web credential path                                              |
| Offline/data            | Bounded offline cash grants in a separate encrypted vault; all server requests still require current authorization                                                     |

## Session and password policy

Passwords are 15–128 characters for onboarding, accept spaces and Unicode, and are never logged or persisted on clients. Node's established scrypt implementation uses N=131072, r=8, p=1, independent random 128-bit salts, and constant-time digest comparison. The versioned encoding pins these parameters; an algorithm upgrade needs an explicit migration/rehash policy. Two hashes may run concurrently per process; overload returns 503. Unknown users incur the same hash cost as known users. See [OWASP password storage guidance](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html). A production breached-password screening service is not configured.

Sessions use opaque random 256-bit tokens, with only SHA-256 token digests stored in PostgreSQL. They expire 30 minutes after login or explicit renewal and always end within 12 hours of initial login. Renewal rotates the token atomically; a previous token cannot be replayed or renewed. An expired session requires password login. There is no long-lived refresh token. At most ten unexpired sessions remain active per account; a new login revokes the oldest excess sessions. The account row serializes login with logout-all. Renew before expiry through the UI; background requests do not extend the session automatically.

Every protected request checks token transport, expiration, revocation and active account status against PostgreSQL. The global guard denies routes by default; currently only health and credential-entry routes have explicit public metadata. Future published reads, narrowly scoped guest commands and anonymous event ingestion require their own guards under D06; this does not authorize exposing an internal controller. Existing health checks stay public. Invalid credentials, disabled accounts, expired and revoked sessions use the same `401 UNAUTHENTICATED` envelope. `403 FORBIDDEN` covers rejected origins and `429 RATE_LIMITED` includes a conservative 900-second Retry-After. Responses are no-store and never expose password hashes or session token hashes.

An authenticated account can list its own sessions, revoke one, log out the current session or revoke all sessions. Guessed session IDs cannot revoke another account's session. Operator disable/enable operations revoke all existing sessions; enabling an account does not resurrect them. No operator endpoint is exposed to ordinary authenticated users.

## Platform storage and CSRF

| Platform                    | Credential handling                                                                                                                                                                                                                                                                                                                                                                  |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Browser, including Expo web | HttpOnly, SameSite=Strict, host-only cookie. Production adds Secure and uses `__Host-inventory_session`; local development uses `inventory_session`. No auth tokens in localStorage, sessionStorage or IndexedDB.                                                                                                                                                                    |
| macOS/Windows Tauri         | Bearer token held only in process JavaScript memory. Reload/restart requires login. Authentication credentials are not persisted in the separate offline business vault. No native SDK is imported into portable/shared code.                                                                                                                                                        |
| Android/iOS                 | Expo SecureStore stores only the bearer token in a namespace bound to the API origin, using device-only, when-unlocked accessibility where supported. The config plugin excludes secure-store entries from Android backups. Storage failure rejects login and attempts server revocation. Tokens restored after reinstall/backup/lifecycle events must still pass online validation. |

Web deployments must put the UI and API on the same site (for example `app.example.com` and `api.example.com`), both on HTTPS. Strict cookies intentionally do not support unrelated-site embedding. During local development use the same hostname for both—prefer `127.0.0.1` everywhere, or `localhost` everywhere; do not mix them. For Expo web opened at localhost, set `EXPO_PUBLIC_API_BASE_URL=http://localhost:3100`. Native devices require a reachable LAN/TLS API, not the computer's loopback address. Use the production build scripts to enforce HTTPS API origins for shipped clients. The Tauri release CSP must explicitly allow the production API origin.

Cookie-authenticated mutations require an allowlisted Origin and the non-simple `x-inventory-client: web` header. Native bearer requests use `x-inventory-client: native`; they ignore cookies and reject unapproved Origins when an Origin is present. Token transport is bound in the database, so a cookie token cannot become a bearer token. CORS credentials are enabled only for configured origins. This applies to login and invitation acceptance as well as authenticated mutations. See [OWASP session guidance](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html) and [Expo SecureStore](https://docs.expo.dev/versions/latest/sdk/securestore/).

## Offline and lifecycle rules

Online management locks on hidden/background events and session expiry, and revalidates on resume and every 60 seconds. Network loss or a transient background read failure alone may retain an already verified in-memory view only until its original expiry; it never renews authority. Explicit denial or malformed session responses clear the view. Reconnection requires fresh authorization for remote operations. A separate passphrase-protected cash register now supports bounded offline grants; see [offline policy](../offline/synchronization.md). Its key is erased on hidden/background events and explicit logout. Offline cash cannot access customer credit, renew an expired session or authorize online routes. Revocations are enforced at upload and offline access lasts at most the eight-hour lease window. Cached product/cart data is hidden at lease expiry; encrypted unresolved operations remain available for authorized recovery.

Renewal requires connectivity and an unexpired session. A failed/uncertain logout locks the UI and reports failure; it does not pretend the server revoked the token. Native secure storage retains the credential for an online retry until expiry or successful revocation; a rejected credential is cleared. Server expiry remains authoritative even if a client clock or timer is changed. The separate offline cash grant has a bounded revocation window and encrypted per-account data/key lifecycle; it never reuses a cached login flag.

## Operator onboarding and account administration

First run `npm run db:migrate -w @inventory/api`. Start the API and clients as documented in the README. Production has no seeded accounts or default passwords. For local development only, the explicit `npm run db:seed:dev` command provisions the [documented test accounts](../../README.md#local-development-login-accounts); it refuses production and remote databases and uses the existing password hashing and authorization model.

`npm run auth:admin -w @inventory/api` builds the CLI and reads a single JSON object from stdin. Paste input and end stdin with Ctrl-D on macOS/Linux. Use the appropriate stdin mechanism on Windows. Supported inputs:

```json
{ "action": "invite", "email": "staff@example.com" }
```

The CLI returns an invitation code once. Treat that output as a secret: avoid CI/application logs and screenshots, deliver it through a trusted channel to the intended person, and have them use **I have an invitation** in any client. Invitations expire after 24 hours, bind the supplied email, and can be consumed only once. Reissuing an invitation replaces the old token; existing accounts cannot be reinvited. Possession of a manually delivered invitation is the onboarding gate, not proof of email ownership. Email is a login identifier and is **not represented as verified**.

```json
{ "action": "disable", "accountId": "00000000-0000-4000-8000-000000000001" }
```

Use `enable` with the same account ID to reactivate, requiring a new login. Account IDs are available in authenticated session responses. Restrict this CLI and database credentials to trusted operators. The runtime role should not administer accounts; provision separate migration/operator credentials and least-privilege runtime access. The CLI's safe failure output omits database details and contact information. Do not place passwords or invitation tokens in command-line arguments.

Run `{ "action": "prune" }` through the CLI daily using a secured scheduler: it removes expired rate-limit buckets and sessions/invitations whose absolute expiration is over seven days old. The API never performs automatic schema changes. The API-only deployment artifact includes `npm run db:migrate` and `npm run auth:admin`; both force production configuration and read injected settings rather than local env files.

No email, SMS, or IdP credentials are needed for manual onboarding or recovery. Automated delivery/verification requires a real provider, securely injected credentials, trusted callback/base URLs, sender setup and delivery-failure handling. No verification or delivery success is simulated.

## Password recovery — Stage 4

After verifying the person's identity through the organization's trusted procedure, a database operator runs `npm run auth:admin -w @inventory/api` and supplies stdin:

```json
{ "action": "recover", "email": "staff@example.com" }
```

The CLI returns a recovery code once. Treat this deliberate operator output as a secret, never as application/CI log content. Deliver it through the trusted channel. Only active existing accounts qualify. Issuance does not change the password or end sessions; issuing a new code invalidates earlier codes. No HTTP endpoint issues codes or reveals whether an email exists.

Web/Tauri and native sign-in screens expose **Forgot password / recovery code**. Enter the account email, code and new 15–128-character password. Completion uses `POST /api/v1/auth/password/reset`, the existing credential rate limits, cookie-origin/header checks and strict input validation. Codes use established 256-bit random tokens, SHA-256 database digests, a 30-minute lifetime and single-use consumption. Successful completion hashes with existing scrypt parameters and atomically changes the password, consumes all codes, revokes every session and revokes old offline grants. No new login session is issued. On an uncertain network response, try the new password before requesting another code.

Disable/enable administration and explicit development credential reset also invalidate recovery codes and offline grants. Account-first locking serializes recovery with login/issuance/logout-all. Tests prove single-use races and rollback of all effects when revocation fails.

Revocation cannot immediately reach disconnected devices: the existing offline grant remains locally bounded by its original expiry (maximum eight hours). Upload of a revoked grant becomes a retained conflict for authorized review; never erase pending sales. Recovery clears the local offline key through the existing lock event. Forgotten offline-vault passphrases cannot be recovered by resetting the account password.

This follows [OWASP recovery guidance](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html) on bounded single-use tokens and explicit login after reset. This application has no MFA enrollment/provider/recovery design to extend; application-level privileged MFA remains an unresolved production risk. Protect operator access with deployment identity controls and separately review a supported MFA/IdP rollout before qualifying privileged production access.

## Abuse controls and deployment limits

Database-backed fixed windows enforce 60 credential attempts per socket IP and 10 per normalized account email per 15 minutes, plus 120 authenticated mutations per session per 15 minutes. Both failed and successful credential attempts count. Rate-limit keys are digests, never raw addresses in logs. Limits are shared across API processes and fail closed if PostgreSQL is unavailable. Direct `X-Forwarded-For` headers are ignored. Behind a reverse proxy the socket IP represents the proxy, so ingress must also enforce per-client limits and deployment capacity must be planned; do not enable blanket proxy trust. Per-email throttling can temporarily delay legitimate users under attack; there is no permanent automatic account lockout.

HTTPS ingress, frontend CSP, restrictive CORS, trusted operator access, database roles, backups and dependency maintenance remain deployment responsibilities. This foundation is not tenant authorization or a completed security certification. Native secure-store behavior needs actual device testing; JavaScript export and mocked adapter tests do not certify a device vault.

## Device recognition and security events — Command 25A

Login now records successful/failed outcomes and recognizes an account-specific installation marker. It is a risk signal, never an authentication factor. New markers transactionally queue in-app alerts for the affected account, active business owners and platform administrators according to policy; permission is rechecked on every inbox read. Active sessions expose their device reference and retain existing individual/all-session revocation. Browser marker cookies are HttpOnly/SameSite and Secure in production; mobile uses SecureStore and desktop uses a non-secret origin-scoped marker. No bearer token storage policy changes. Recovery/renewal/revocation and sensitive settings are audited; credential throttling records threshold events separately. See [routing, retry, retention and production limits](../development/command-25a.md). MFA and external notification providers remain unimplemented.

The catalog WebSocket uses a separately issued 30-second single-use ticket, hashed and atomically consumed in PostgreSQL. Issuance requires the current authenticated session and `products.read` scope; each hint revalidates account/session/membership access. Browser Origins are allowlisted; native handshakes identify the runtime with a custom header but still require the ticket. Session tokens never enter the socket URL. See [live protocol and limits](../development/live-ui-refinement.md).

## Approved storefront and analytics boundary — implementation pending

[Milestone 1 D06 and D11](../decisions/milestone-1.md) preserve invitation-only workforce identity, browser HttpOnly cookies, ephemeral desktop credentials and native SecureStore. Guest checkout/status never grants staff membership or reuses an employee session as public authority. Published reads may be explicitly cached as a separate safe projection; private/authentication responses remain no-store. Guest status tokens must be opaque, digest-stored, bounded, revocable, scoped and redacted from logs/referrers. They are not staff sessions or offline grants. Public commands/ingestion need their own abuse/origin/CSRF controls; existing protected-route defaults remain unchanged until reviewed implementation.

Analytics v1 is online-only with optional last-loaded **in-memory** aggregate display marked cached/as-of. Clear on account/business/access change, logout, expiry, denial, malformed access validation, background/visibility lock or restart. No persistent analytics storage and no extension of session or offline lease lifetime. An outage does not permit refunds, order administration, purchasing or inventory mutations.

Release qualification is governed by [the platform checklist](../release/qualification.md): web, Windows and macOS are launch-gated; mobile parity remains required while native mobile qualification is tracked separately. Historical validation tables are not current release approval.
