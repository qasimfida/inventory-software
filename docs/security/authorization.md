# Tenant authorization and security

Authentication establishes identity; authorization decides allowed actions on specific resources. Invitation onboarding and session/token policy are implemented in [authentication](authentication.md). Never trust a client-supplied business ID, hidden button or shared client validator as enforcement.

- Resolve active business membership server-side, then evaluate permission, role, branch/store/warehouse scope, resource ownership and approval requirements on every command/query. Deny by default. Sensitive permissions include price overrides, refunds, adjustments and cross-business trade.
- Include tenant keys in business rows, scoped unique constraints and foreign-key relationships so cross-tenant references cannot be formed accidentally. Repository queries, joins, exports, aggregates, jobs, sync feeds and sockets all need tenant filtering. A guessed UUID is not authorization.
- Inter-business trade uses separately authorized participants and minimal disclosure. Do not grant one business access to the other's private inventory, pricing or customer records through a shared correlation ID.
- PostgreSQL RLS is proposed defense in depth for tenant tables. At schema implementation, evaluate coverage, use a non-owner runtime role without BYPASSRLS, consider FORCE ROW LEVEL SECURITY, and set tenant context transaction-locally to prevent pooled connection leakage. Migration/admin roles stay separate. Test policies using the actual runtime role; application permissions still apply.
- Reauthorize queued offline commands when received. Define signed/validated offline capability scope, device binding, expiration and permitted actions before enabling offline login/work. No indefinite offline authorization; disclose revocation latency. Rejected work stays protected for authorized resolution.
- Partition local caches and secure credentials; use native secure storage and an explicit browser session/threat model. Encrypt sensitive local data where required with a real key lifecycle; encryption with exposed keys does not protect shared terminals. Address XSS, CSP, CSRF if cookie-based, TLS, input validation and rate limits during implementation.
- Audit sensitive attempts and changes with actor, business/resource scope, operation/correlation ID, timestamp, reason, approval and safe before/after references. Protect audit integrity and restrict reading. Never log passwords, tokens, payment secrets or unnecessary personal data.
- Secrets stay outside source control; document variable names with fake examples only when introduced. Logs and errors must not reveal other tenants' existence or sensitive records. Payment data should remain with the provider wherever possible.

Security acceptance includes cross-tenant IDs, mismatched nested resources, insufficient warehouse scopes, revoked users, feed/socket access, background jobs, cache switching and RLS role behavior. Use [testing](../development/testing.md) and update this policy with each new authorization surface.

## Current foundation enforcement

Public endpoints are live/ready health checks and guarded, rate-limited login/invitation acceptance/password-reset completion. Recovery-code issuance remains operator-only. Other controller routes require an active session by default. The API binds loopback by default, validates environment variables, uses verified PostgreSQL TLS in production, allowlisted CORS, Helmet, request-size defaults, generated request IDs and safe JSON errors/logs. Exact packaged Tauri origins are documented exceptions to browser HTTPS origins. CORS is not authorization. Authentication and tenant-scoped organization management are implemented. See [organization management](../development/organization-management.md) for the exact role matrix, immutable parent relationships, lifecycle rules, audit behavior and the evaluated/deferred RLS decision. Every future internal business endpoint must use equivalent authenticated scope enforcement. The separately approved public/guest surfaces below require explicit alternative guards; they are not exemptions for internal endpoints.

Mobile uses Expo SecureStore; desktop deliberately retains credentials only in memory. Client environment variables are public. Database-backed authentication rate limits and origin/header CSRF checks are implemented. Production deployment still needs ingress abuse controls, HTTPS, signing and secret provisioning. [Validation status](../development/validation-status.md) records unresolved transitive mobile-tooling advisories; do not claim dependency security clearance or deploy unsigned/unqualified shells.

Scoped managers, cashiers, custom permissions and operator-provisioned super administrators are implemented. [Domain rollout](../development/domain-rollout.md) defines the current grants, scope behavior and audit protections; it supersedes the earlier owner/manager/viewer-only matrix.

Catalog, stock, purchasing, storage and transfer routes now use OrganizationScope and granular domain permissions. Supplier/catalog metadata is business-shared; stock and documents enforce warehouse/store scope. Transfers require access to both endpoints. See [domain rules and validation](../development/domain-rollout.md); shared client controls never authorize an API operation.

Commerce uses dedicated `customers.credit`, `customers.override`, `sales.refund`, `sales.void` and `payments.cash` permissions. Cashiers can sell and collect cash but receive none of these privileged defaults. Profile payloads cannot change credit policy. Every operation reacquires tenant membership/scope under the organization transaction lock before checking/replaying idempotency. Statements/refunds restrict warehouse-visible financial history; aggregate credit exposure remains server-side across all customer invoices. Audit entries omit customer name/contact/notes. Retention anonymizes inactive, settled profiles only; it preserves financial identifiers and evidence. Staff must not put contact data into financial reference or reason fields.

Stage 5 report authorization combines `reports.read` with each owning domain's read permission and current membership store/warehouse scope; the business URL and optional warehouse filter never confer access. Operational notifications revalidate the recipient's permissions/scope on reads and acknowledgements. Approval review uses existing backend document commands and versions; notification delivery/read status grants no permission. See [report and notification policy](../development/stage-5.md).

Stage 6 trading is business-wide `business.write` only; invitation acceptance is restricted to the invited party, and every shared order/history query checks the current authenticated business is one of its two parties. No business directory is exposed. Accounting rejects store/warehouse-scoped memberships and requires `reports.read`, `payments.read`, `sales.read`, `purchases.read`; writes also require `reports.write` and `payments.write`. These are compositional existing permissions, not new grants to custom roles. Integration status requires `business.read`; AI navigation applies fresh authorization before and after provider execution and durable account/business request limits. External provider secrets and arbitrary database access never reach clients or the model.

## Milestone 1 approved extensions — not yet implemented

[Decisions D04–D11](../decisions/milestone-1.md) define the following future boundaries. Current APIs and permission enforcement are unchanged by these records.

- Storefront management requires explicit `onlineStore.manage`, `onlineStore.orders` and `onlineStore.analytics.view` capabilities as appropriate, plus current tenant/location scope. UI visibility, enabled storefront state and notification receipt never grant authority. These permissions still require implementation and role/delegation review.
- Public reads use an enabled, published-only allowlisted projection resolved by slug. Exclude cost, suppliers, private notes, exact stock and customer PII. Published reads are distinct from narrow guest commands and event ingestion. All three recheck storefront/tenant boundaries; guest commands revalidate prices/availability and stable operation IDs. Never expose internal catalog/sales endpoints.
- Guest order-status tokens authorize only minimal status for one order/business, not general customer lookup, order mutation or employee access. Apply expiry/revocation, digest storage, URL/log/referrer redaction and rate limits. New public limits must use reviewed proxy/client identity, not unchecked forwarded headers. Telemetry is PII-free, approximate, consent/DNT-aware and retained for a bounded configured period.
- Refunds at or above the configured cumulative per-sale currency threshold require separate authorized approval in the existing queue; missing policy requires approval. Prevent request splitting, self-approval and reuse after payload/version changes. Request, decision and execution are distinct audited events. Recheck refund/approval permissions, scope, remaining refundable amount and cash constraints on execution. The existing queue must be extended; it currently does not implement this policy.
- Custom adjustment codes are business-owned, administration-gated and retained historically when deactivated. Codes do not confer stock-write authority. Undo is an authorized compensating transaction with the original source retained, never data deletion.
- Manual bank/COD collection and clearing reconciliation require explicit payment authority, evidence and audit; a customer claim, shipment or notification cannot mark a payment paid. Approval and collection remain online-only.
- Analytics shares the authoritative POS/online aggregation and business-timezone/net-return definitions in D11; internal reporting retains both report and underlying domain permissions. Only already authorized aggregate data may remain in memory during a transient outage, until normal expiry/lock. No persistent analytics cache or offline authorization expansion.
- Customer notifications require separately configured delivery with minimal PII, retries and honest delivery status. Staff notification access remains revalidated. Public publication changes and disablement must invalidate caches and fail closed for new checkout while preserving authorized handling of existing orders.

Media must use trusted sources and a narrow policy on each platform. The base desktop CSP blocks remote images; profile packaging now permits only the exact HTTPS origins configured in `DESKTOP_IMAGE_ORIGINS` (unset means none). Browser allow/deny checks do not replace installed-WebView qualification. Validate the final merged artifact and deny untrusted hosts/internal-network fetching; see [release qualification](../release/qualification.md).
