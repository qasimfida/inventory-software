# POS & INVENTORY MANAGEMENT PLATFORM
## Complete Implementation Playbook — Commands 2–35

# GLOBAL INSTRUCTIONS FOR EVERY COMMAND

Apply these rules to every command below.

### A. Inspect before implementing

Before changing code:

1. Read `AGENTS.md` and the relevant specialized documentation.
2. Inspect the actual repository, existing implementations, API contracts, database schema, tests, and platform adapters.
3. Identify what is already implemented, partially implemented, missing, duplicated, or broken.
4. Trace affected consumers, dependencies, events, caches, persistence, and supported platforms.
5. Write a concise implementation plan before editing.
6. Reuse working code and preserve backward compatibility unless a justified change is required.

Never assume that a feature is missing just because its implementation is not in the expected file or folder.

### B. Platform coverage

Unless a task explicitly specifies a platform, implement the feature across all applicable supported platforms: web, mobile, Windows, and macOS.

Share domain rules and API contracts wherever possible. Use platform-specific adapters for local databases, hardware, secure storage, and native capabilities.

If a platform cannot support the requested behavior, document the limitation and provide a suitable alternative. Do not silently omit a supported platform.

### C. Code quality

- Prefer focused files around 100–150 lines; treat 200 lines as a review threshold rather than an absolute limit.
- Follow the existing architecture and component boundaries.
- Use strict TypeScript wherever TypeScript is used.
- Keep UI, domain logic, persistence, API controllers, and platform integrations separate.
- Use shadcn/ui for suitable low-level web UI primitives, `src/components/common/` for reusable application components, and feature-specific folders for feature-owned components.
- Avoid duplicate logic, unnecessary dependencies, giant components, hardcoded configuration, dead code, and excessive comments.
- Never disable tests, weaken type safety, or suppress errors merely to achieve a passing build.

### D. Data integrity and security

- Enforce tenant isolation and permissions on the backend.
- Use database transactions for operations that must succeed or fail together.
- Make retryable write operations idempotent.
- Preserve auditability for sensitive business operations.
- Do not use blind last-write-wins for inventory, sales, payments, or financial records.
- Never expose secrets or sensitive business data in logs.
- Do not trust client-side calculations or permissions as the authoritative source.

### E. Completion requirements

For each command:

1. Implement only the assigned scope.
2. Add or update tests.
3. Run relevant formatting, lint, type-check, tests, migrations checks, and builds.
4. Inspect the diff for regressions and unnecessary changes.
5. Update documentation when necessary.
6. Report files changed, actual validation results, limitations, and remaining work.
7. Stop and wait for approval before starting the next command.

Do not claim a test passed unless it was actually executed successfully.

- Traceability from each movement to its originating business operation.
- Reconciliation between ledger totals and materialized balances.

Do not implement stock changes by directly overwriting quantities. Correct mistakes through explicit reversals or adjustment movements.

Define the difference between on-hand, reserved, available, damaged, and in-transit stock if those states are supported.

Test duplicate requests, simultaneous sales, rollback after partial failure, negative-stock restrictions, and balance consistency.

Document the accounting of stock movements and migration strategy. Stop.

## COMMAND 15 — Implement Internal Stock Transfers

# STAGE 4 — OFFLINE-FIRST OPERATION

## COMMAND 21 — Implement the Local Persistence and Synchronization Engine

Inspect the existing offline interfaces and platform storage implementations before writing synchronization logic.

Implement the actual offline foundation for approved platforms.

Requirements:

- Durable local storage.
- Local schema versioning and migrations.
- A persistent outbox for supported operations.
- Stable operation identifiers.
- Idempotent server-side processing.
- Batched uploads.
- Incremental downloads using server-defined cursors or versions.
- Retry with bounded backoff.
- Durable checkpoints.
- Network interruption recovery.
- Synchronization status and error reporting.
- Conflict detection and resolution workflows.
- Protection against duplicate application of changes.
- Recovery after application crashes or device restarts.

Use IndexedDB or a suitable browser persistence layer for web, and an appropriate SQLite-based solution for desktop and mobile when supported.

Separate synchronization transport from domain rules. Do not use sockets as the durability mechanism.

Define conflict policies by operation type. Inventory and financial operations require domain-aware reconciliation, not blind last-write-wins.

If a device-local operation cannot be safely replayed, surface it as unresolved rather than silently discarding it.

Add failure-injection tests for interrupted requests, repeated requests, application restarts, stale cursors, and corrupted or incompatible local schema versions.

Do not claim complete offline support until the supported operations have been integrated and tested. Stop.

Integrate the synchronization engine with the POS flow.

Support:

- Durable offline carts and sales.
- Locally generated stable transaction identifiers.
- Configurable offline payment policy.

## COMMAND 23 — Implement Real-Time Updates and Reconnect Recovery

Implement real-time notifications for relevant changes, including approved price updates, product changes, inventory changes, and operational status changes.

Use the established backend event mechanism, such as Socket.IO, where suitable.

Rules:

- The database remains authoritative.
- Events notify clients that data may have changed.
- Clients recover missed changes through the synchronization or delta API.
- Events must be scoped to authorized businesses, stores, and subscriptions.
- Reconnection must not depend on receiving every previous socket message.
- Use event identifiers, versions, or cursors where needed.
- Prevent duplicate event handling from duplicating business operations.
- Avoid broadcasting sensitive data to unauthorized clients.

Ensure price updates reach the relevant POS screens and cached price snapshots. Define behavior when a terminal is offline or a price version is stale.

Add reconnect, missed-event, duplicate-event, authorization, and stale-cache tests. Do not add unnecessary real-time dependencies to unrelated screens. Stop.
