## Design decisions and alternatives

**Recommend a parent combined bill with one child sale per store.** Each child owns its stock movements, pricing, tax snapshot, receivable and receipt. The parent is a collection/summary document, never another sale or another revenue source.

| Choice                                               | Effects                                                                                                                                                                                    | Recommendation                                                                                            |
| ---------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------- |
| Child sale per store                                 | Branch revenue/tax/returns remain with the branch; cash collection needs inter-store clearing; child receipts remain independently auditable.                                              | Adopt. Matches the requested branch reporting.                                                            |
| One selling-store sale, remote warehouse fulfillment | Selling store receives all revenue and tax attribution; remote locations supply stock only. Returns and fulfillment require additional cross-warehouse rules; branch sales reports differ. | Reject for D1; this is a different operating model, not a simpler implementation of the same requirement. |
| Client submits several normal checkouts              | Can partially complete, duplicate tender/change and require several shifts.                                                                                                                | Reject. One authorized server transaction is mandatory.                                                   |

Proposed v1 boundaries requiring approval:

1. **One currency and one selected checkout warehouse per participating store.** Per-line store/warehouse is explicit, but all lines within a store must share that store's selected warehouse in v1. Supporting multiple warehouses inside one child sale requires a larger sale/return schema change; do not silently split into multiple children per store.
2. **Store-local customers:** walk-in cash needs no customer. For named/credit sales, choose or explicitly confirm an existing customer separately in every relevant store. Parent retains a display recipient snapshot plus child customer links; it does not create a new shared credit identity. Never auto-link by name/phone or copy a credit limit.
3. **Permission scope:** initially “My stores” means every active store already allowed by existing membership/location rules. A single-store cashier cannot use it to escape their scope. No new multiple-store membership system in D1.
4. **Cash and authorized credit only.** No card/bank additions. Cash allocations are explicit per child, prefilled by deterministic child order up to each total; show and allow review before confirmation. Remaining amounts require that child's valid customer and credit policy. Aggregate cash received/change is entered once.
5. **Ledger prerequisite:** implement Feature C's branch attribution, locked system clearing accounts and source reconciliation before enabling D1 checkout. For this new grouped command only, recommend atomic posting of child sales, allocated collection and clearing in an open period. Missing period/setup blocks D1 with an actionable message; existing single-store checkout stays unchanged. This explicitly differs from C's proposed separate posting for legacy commands and needs approval.
6. **Numbering:** add an immutable parent bill reference and store-specific child receipt references for grouped sales, while retaining UUIDs and legacy receipt identities. Use a business/store-scoped locked counter, unique constraints, no reuse after void. Do not claim tax-invoice legal compliance or fabricate tax-registration settings; preserve available business/store identity snapshots.
7. **Refund location:** recommend the original collecting store's currently open authorized shift for refunds of grouped collections. Require authority over both selling and collecting locations. Supporting arbitrary refund branches is deferred; do not silently use the selling till.

## Proposed data and invariants

- `bill_groups`: business/id/reference, collecting store/warehouse, currency, recipient snapshot, original net/tax/total, tendered/applied/change, actor/time and operation reference. Posted economic fields are immutable; return/payment summary states derive from linked facts.
- `bill_group_children`: business/group/store/sale/customer links, original allocation; unique group/store and unique sale membership. Tenant-composite FKs prevent foreign-business children. Existing sale owns warehouse and line snapshots; parent line projection derives store/warehouse from child, without duplicated editable stock data.
- `bill_collections`: one confirmed physical tender at collector, shift, currency and original received/change/applied amounts. `bill_collection_allocations` links exact amounts to each child and its cash-payment evidence. Allocation sum equals applied cash; received minus change equals applied cash.
- Preserve sale-linked payment rows for existing receipt/AR/refund consumers, but explicitly mark their grouped collection source and physical collecting location. Their shift entries sum to the one net collection; never additionally add a parent shift entry for the same amount. Parent collection is summary evidence, not an extra cash source.
- Update cash/source/report consumers to distinguish selling-store attribution from actual cash location. Existing cash-payment journals must use the grouped allocation mapping for grouped records, not the legacy Dr cash/Cr AR mapping as an additional posting.
- `bill_settlements`: immutable transfer evidence between collector and selling store with from/to shifts/accounts, currency, amount, actor, command and reversal link. Balances derive from journal/settlement evidence, not mutable outstanding columns.
- New journal clearing accounts require Feature C's chart support; use store and counterparty dimensions, not arbitrary per-bill chart accounts. No intercompany accounts: all stores belong to the same business.
- Receipt counters and snapshot metadata are additive. Never rewrite old receipts, taxes, sale totals or journals to fit grouped billing.
- Forward migration creates structures and constrained optional links; legacy sales remain ungrouped. Backfill only proven attribution. Disable grouped commands as an operational rollback, retain readable posted groups and all evidence; never drop used financial records.

## Atomic checkout and reconciliation

1. Resolve authenticated business context once. Reauthorize sales permission and all active stores/warehouses/locations, collector/terminal, customers and payment capabilities before operation-receipt replay or posting.
2. Validate bounds (proposed maximum 10 stores and 50 total lines), one currency and one warehouse per store. Lock all stock keys and relevant credit/shift/accounting resources in deterministic order inside the existing business transaction.
3. Requote every child through existing pricing and compare an aggregate fingerprint binding child quotes, locations, customer mappings, allocations and collector. A changed quote requires review, not silent repricing. Do not reserve stock merely by previewing.
4. Validate every credit obligation and total exposure, every cash allocation and actual collector shift. Full-credit grouped bills need no cash shift; credit and all accounting preconditions still apply.
5. Create group and child sales using extracted transaction-local sale-writing/payment-allocation helpers. Reuse LedgerCore and ReceivableCore; do not call separate service transactions or pass fake offline quotes to bypass validation.
6. Record collection allocation evidence, net till cash, journals/clearing, references, audit, operation receipt and existing change notifications in that transaction. Any child failure rolls back all children, stock, money, allocations and counters.
7. Return the confirmed parent and child references. A lost response freezes editing and recovers the original operation; it never automatically starts another bill. Parent status is not inferred from a transport timeout.

Example (illustrative minor units, no tax for readability): Gilgit A sells 1,000, Gilgit B sells 2,000; A collects 3,000.

- A sale: Dr settlement/AR 1,000; Cr revenue 1,000. B sale: Dr settlement/AR 2,000; Cr revenue 2,000. Real tax splits still use each quote.
- A local allocation: Dr cash(A) 1,000; Cr settlement/AR(A) 1,000.
- B allocation collected at A: Dr cash(A) 2,000; Cr due-to B(A) 2,000; Dr due-from A(B) 2,000; Cr settlement/AR(B) 2,000.
- A till increases by 3,000 once, B till by zero. Revenue remains 1,000/2,000 by branch. Business clearing cancels on consolidation; cash and revenue are not posted again for the parent.
- Later physical settlement of 2,000: A Dr due-to B/Cr cash(A); B Dr cash(B)/Cr due-from A. Both actual shifts must be authorized/open, source cash sufficient and both sides commit together. Retaining centralized cash is allowed; an unsettled balance is explicit, not silently cleared.
- Customer credit portions remain child AR and create no inter-store cash clearing until actual collection. Later collection at another store uses the same allocation/clearing rules and must not call a single-store collector incorrectly.

Receipt and reconciliation acceptance: parent total equals child totals; each child total less returns equals allocated payments less refunds plus outstanding; net collector shift entries match collection evidence; due-to equals due-from by store pair/currency; all relevant source journals occur once. Existing source posting commands must recognize already-posted grouped sources and never duplicate them.

## Returns, voids and state transitions

- Client: editing → quoting → review/payment → submitting → confirmed, or uncertain → authorized status recovery. Definite validation failure returns to editable review; unknown outcome never does automatically.
- Parent business state derives from children: completed, partially returned, fully returned, or voided only when all children are voided. Mixed returned/voided states remain accurately described; no parent delete or blind “undo all.”
- Return/void one child using its original lines, cumulative rounding, stock location/disposition and credit-before-refund policy. Parent summary links those facts, without changing other children.
- Group refund preserves original payment capacity and the collecting shift context. Reverse related clearing as the refund is actually paid. If stores have already settled, allow an explicit reverse obligation rather than deleting settlement history; physical cash transfer remains a separate authorized event.
- Require existing refund/void permissions and configured approval policy, including cumulative thresholds and no self-approval. An absent or incomplete approval implementation is a prerequisite blocker, not permission to bypass it.
- Linked source corrections also post the exact compensating journals. A journal-only reversal cannot undo stock, payment or allocation.

## API and access proposal

All paths below are proposed additions under `businesses/:businessId/sales`; existing single-sale contracts remain supported.

| Endpoint                           | Purpose                                                                                                                         |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| `GET multi-store/items`            | Bounded authorized search with store/warehouse badges, price/currency and availability; paginated server-side.                  |
| `POST bill-groups/quote`           | Child carts, selected warehouses/customers and collector; server totals and fingerprints, no stock reservation.                 |
| `POST bill-groups`                 | One stable operation key and reviewed allocation payload; atomic group checkout.                                                |
| `GET bill-groups/:id`              | Parent summary/receipt only with access to all participating stores; branch-scoped users use their existing child sale details. |
| `GET bill-groups/operations/:key`  | Read-only result recovery bound to actor, current tenant access and complete group scope.                                       |
| `POST bill-groups/:id/settlements` | Authorized physical inter-store cash settlement; stable key, exact amount and journal linkage.                                  |

- Proposed `sales.multiStore` capability defaults to business owner/admin, with explicit role assignment for others; it supplements `sales.write`, never overrides scope. Settlement additionally requires cash and accounting permissions at both locations. New names/defaults need shared contracts, server checks, UI gating and tests.
- Replays and child/parent exports reauthorize all resources. Users losing one store cannot retrieve complete group details or hidden-store totals through status, notifications, search or parent IDs. Their allowed child receipt remains usable.
- Use shared SchemaPipe/Zod contracts, safe domain error codes and secondary correlation IDs. Identify changed items, insufficient stock, customer mismatch, closed shift and missing accounting setup without leaking inaccessible records.
- A combined customer receipt requires full group access; it is labeled a summary and references each child receipt. Printing failure never rolls back a sale or triggers checkout again.

## Platform UX and offline behavior

- Keep `/pos`. Add “This store / My stores” scope only when authorized; store badges on product results and cart lines, grouped cart sections with child subtotal/tax and aggregate payment footer. Keep compact shared components and existing preference resolution.
- A line's merge identity includes store, warehouse, variant, unit, location and discount: the same SKU in two stores must remain separate. Barcode search with multiple matching stores asks for a source; no silent first-store selection.
- Changing scope/warehouse cannot silently move existing lines or reset the cart. Explain incompatible changes; block switching while submitting/uncertain. Customer mapping and cash allocation review use existing drawers/native panels.
- Web/Tauri retain responsive sticky payment controls; mobile uses native groups and cart dock with the same shared model/contracts. Keyboard/scanner input, focus restoration, large text, reduced motion and touch targets remain supported.
- Sales history retains child store reports and adds an authorized parent link/detail. Reuse receipt text/print adapters for separate child receipts and combined summary; do not depend on Feature B's unapproved PDF renderer.
- D1 is online only, including a desktop local-network deployment: “online” means the authoritative configured API is reachable, not necessarily public internet. On disconnection retain the in-memory group draft and disable confirm with a clear message; do not convert it into separate offline sales or put it in the single-warehouse vault/outbox.
- Existing prepared single-store offline cash remains unchanged. Switching to it requires explicit handling of the unsubmitted group; unknown submissions stay locked until status recovery. Session lock/expiry follows existing sensitive-state rules; do not promise restart persistence without an approved safe recovery mechanism.
- Required scenarios: loading, no eligible stores/products, no search results, denied, changed quote, validation errors, closed shift, missing customer mapping, missing ledger setup, offline draft, submitting, uncertain, confirmed, print failure, unsaved changes and authorized correction confirmation.
